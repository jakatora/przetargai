## [CRITICAL] firebase/functions/src/db/repos.js:183

**openPool() drugie zapytanie wymaga indeksu złożonego, którego brak — cały silnik dopasowań rzuca wyjątek**

- Scenariusz: tenders.openPool() odpala col.where('deadline','==',null).orderBy('fetched_at','desc'). To equality na jednym polu + orderBy na INNYM polu, więc Firestore wymaga indeksu złożonego (deadline, fetched_at DESC). W firestore.indexes.json jest tylko pojedynczy indeks matches/created_at — tego composite indexu NIE ma. Wynik: openPool() rzuca zawsze. - Naprawa: Dodać do firestore.indexes.json indeks złożony dla collectionGroup 'tenders' z polami [{deadline, ASCENDING},{fetched_at, DESCENDING}] i wdrożyć (firebase deploy --only firestore:indexes). Pierwsze zapytanie (where deadline > now + orderBy deadline na TYM SAMYM polu) indeksu nie wymaga i działa.

## [CRITICAL] firebase/functions/src/db/repos.js:183

**openPool() null-deadline query needs a composite index that doesn't exist — entire matching pipeline throws**

- Scenariusz: openPool() runs `where('deadline','==',null).orderBy('fetched_at','desc')` inside Promise.all. Firestore requires a composite index whenever an equality filter is combined with orderBy on a DIFFERENT field (deadline ==, fetched_at DESC). firestore.indexes.json contains only a collectionGroup index on matches/created_at — no such tender composite index. At runtime the query fails with FAILED_PRECONDITION 'The query requires an index'. Because it runs under Promise.all, the whole openPool() rejects. generateMatchesForAllUsers() (matching.js:148) awaits openPool() outside any try, and runTenderFetch() (jobs/fetchTenders.js:34) calls it outside its try block, so the daily cron AND admin POST /admin/fetch-tenders both 500. backfillUser() (registration + PATCH /auth/me) also throws but is swallowed by the fire-and-forget .catch, so users silently never get matched. Net effect: no match is ever created in production — the core product is dead on Firestore.
- Naprawa: Add the composite index {collectionGroup:'tenders', fields:[{deadline, ASCENDING},{fetched_at, DESCENDING}]} to firestore.indexes.json and deploy it, OR drop the orderBy on the null branch (order by deadline/document id instead) so it stays a single-field query. Also wrap openPool() callers so a query failure degrades gracefully instead of crashing the whole cron.

## [HIGH] firebase/functions/src/routes/auth.js:146

**Denial-of-wallet: PATCH /auth/me toggling keywords triggers unbounded full-pool Firestore reads**

- Scenariusz: PATCH /auth/me is mounted under the loose apiLimiter (app.js:72, 120 req/min per IP), NOT the strict guessing limiter. Whenever keywords/cpv_codes differ from the stored value, criteriaChanged is true and backfillUser(updated) fires (fire-and-forget, errors swallowed). backfillUser -> openPool() reads up to `limit` (default 2000) tender documents (the first deadline>now query executes and is billed even though the second branch later errors per finding #1). An authenticated attacker alternates keywords `['a']`/`['b']` on each request: 120 PATCH/min/IP x ~2000 reads = ~240k billed Firestore reads/min per IP, from any number of IPs, with no per-user throttle and no dedup of concurrent backfills. aiQuota caps only paid AI calls, not read cost, so nothing bounds this. Real monetary drain plus memory/CPU pile-up from stacked fire-and-forget runs.
- Naprawa: Throttle re-matching per user (e.g. debounce/cooldown on backfill, or a per-user daily backfill counter in Firestore), and/or run backfill via a queue instead of inline fire-and-forget. Cap openPool reads and skip backfill when it would exceed a budget.
