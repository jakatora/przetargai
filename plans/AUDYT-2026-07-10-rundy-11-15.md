## [HIGH] firebase/functions/src/lib/clientKey.js:26

**Rate-limit key uses spoofable 2nd-to-last X-Forwarded-For entry, contradicting `trust proxy 1` → login/admin limiter bypass**

- Scenariusz: App runs on the default direct cloudfunctions.net/api URL with app.js `app.set('trust proxy', 1)` (one trusted appended hop). Google's front end appends the real client IP as the LAST XFF entry, so the header is `<client-supplied>, <realClientIP>`. kluczKlienta takes `wpisy[wpisy.length-2]` = index 0 = the client-supplied value (req.ip is only a fallback and is never reached because index 0 is non-empty). An attacker POSTing /auth/login with `X-Forwarded-For: <random>` on each request gets `<random>, <realIP>` → keyGenerator returns the random value → a brand-new rate-limit bucket every request. The 30-per-15min brute-force limiter and the 20-per-15min admin-key limiter never trigger. Because the production header has exactly 2 entries, `przedostatni === wpisy[0]` — identical to the pre-fix `wpisy[0]` behavior, so the fix did not actually close the bypass on this deployment. Correct pick under `trust proxy 1` is the LAST entry (or just req.ip).
- Naprawa: Consistent with `trust proxy 1`, key the limiter on the last XFF entry: `const zNaglowka = wpisy[wpisy.length - 1]`, or simply use `ipKeyGenerator(req.ip)` and delete the manual XFF parse. `przedostatni` is only correct behind an external HTTPS load balancer that adds a second trailing hop — which the default cloudfunctions.net URL does not have.
